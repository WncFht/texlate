# docs/ 维护规则

本文档库的唯一维护契约：写新件、改旧件、登记索引、发布前检查都先读这里。仓级入口约定见根 `AGENTS.md`；贡献者上手序见 `dev/README.md`。

## 1. 分区结构与生命周期

| 分区             | 读者   | 内容                                       | 生命周期                                                                |
| ---------------- | ------ | ------------------------------------------ | ----------------------------------------------------------------------- |
| `guide/`         | 用户   | 安装上手、CLI、web 服务、BYOK、导出共享    | 活文档，随版本更新                                                      |
| `spec/`          | 实现者 | 各层技术规范，**实现的唯一事实源（SSOT）** | 活文档，与代码现状对齐                                                  |
| `decisions/`     | 所有人 | ADR 决策记录：为什么这么定                 | 只增不改（子结论改判走宿主 ADR「演变」节）；整篇作废才开新 ADR          |
| `dev/`           | 贡献者 | 仓布局、工具手册、评测协议、自动化契约     | 顶层只放活文档；一次性工作包收 `dev/projects/`，封存件收 `dev/archive/` |
| `research/`      | 实现者 | 调研与实证档案，决策的证据层               | 写完冻结，可加状态注记                                                  |
| `log/`           | 所有人 | 工程大事记与里程碑档案                     | 只增不改                                                                |
| `README.md`      | 所有人 | 文档库总索引与阅读序                       | 活文档                                                                  |
| `MAINTENANCE.md` | 维护者 | 本文                                       | 活文档                                                                  |

## 2. 文件形态（kind）定规

每件入库文档恰属一种形态；形态决定落点、冻结性与状态标记义务。

| 形态     | 是什么                                          | 家                             | 冻结                         | 状态标记                           |
| -------- | ----------------------------------------------- | ------------------------------ | ---------------------------- | ---------------------------------- |
| 活文档   | 现行契约/手册/规范，随代码同步改                | `spec/`、`dev/` 顶层、`guide/` | 永不冻结                     | 免（dev 顶层由 README 状态列代管） |
| 工作包   | 一次性执行计划/工单/实施包（plan、实现 bundle） | `dev/projects/`                | 收口即冻结                   | 包内件带状态块                     |
| 封存件   | 被取代的方案、固化的时点普查                    | `dev/archive/`                 | 入库即冻结                   | SUPERSEDED/时点横幅                |
| 调研报告 | 取证/选型/逆向证据                              | `research/`                    | 写完冻结，可加注记           | 状态块（§6）                       |
| 大事记   | 里程碑、收官报告、编年档案                      | `log/`                         | 只增不改                     | 状态块                             |
| ADR      | 裁决记录                                        | `decisions/adr/`               | 只增不改（改判走「演变」节） | 「现状」节                         |
| 索引     | 层/域/目录 README                               | 各层各域                       | 随成员更新                   | 免                                 |

铁律：

- **`dev/` 顶层纯活文档**——任何「写一次不再改」的件不许留顶层：在执行与已收口工作包一律进 `dev/projects/`（执行计划也算工作包，不因「还在跑」就例外）；被取代/封存进 `dev/archive/`。
- **`-plan` 后缀闸**：活契约与 spec 件永不带 `-plan`/`-impl` 后缀——计划性命名即宣告「此件有寿命」，寿命尽时必迁出顶层。同理实现包整目录进 `projects/`，不拆散。
- **spec 升格**：被代码注释以路径串引用的契约件必须升格进 `spec/`——代码注释是引用面最硬的检索道，注释要 `grep` 得中。spec 件命名不带日期、不带状态词。
- **research/ 是证据层不是工单层**：活执行计划、在跑工单不放 `research/`（冻结语义冲突）——归 `dev/projects/`。
- **`log/` 只进收官/里程碑实录**：在执行过程账与 append-only 台账放各自工作件（如 `dev/bench-massrun-plan.md` 自身即台账），收官时才向 `log/` 归档。

## 3. 变更归层：写什么放哪

按变更性质选落点；一件变更常跨两层（如 spec + log 同步）。

| 变更                            | 落点                                                                                                                                                             |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 代码行为、接口、契约变化        | `spec/` 对应件，与代码同提交更新                                                                                                                                 |
| 用户可见行为、安装/上手路径变化 | `guide/` 对应件                                                                                                                                                  |
| 推翻或修正既有裁决              | 子结论改判 → 记宿主 ADR「演变」节 + 更新「现状」节与日期行，不单独占号；整篇作废 → 新 ADR 进 `decisions/adr/` + 旧文加 SUPERSEDED 横幅（不删文、不改写历史正文） |
| 新实测数据、调研、审计证据      | `research/` 对应域新文件 + 域 `README.md` 登记一行                                                                                                               |
| 开工执行计划 / 工单             | `dev/projects/` 新件或新目录；收口干 Readme 状态列翻「已收口」                                                                                                   |
| 里程碑、审计、发布、阶段收官    | `log/` 当日目录或文件 + `log/README.md` 时间线续记                                                                                                               |
| 仓布局、工具链、操作流程变化    | `dev/` 对应件                                                                                                                                                    |
| 决策动机存疑但暂无新裁决        | 不动 `decisions/`；新证据落 `research/`，相关 ADR 可加注                                                                                                         |

## 4. spec/ 纪律（事实源）

- `spec/` 与 `src/texlate/`（bench 件与 `bench/`）代码现状一一对齐。发现文档与代码漂移：以代码为准改文档；若判定代码该改而非文档，先记漂移再报决策，不抢先改规范。
- 规范只写「是什么/怎么约束」；实测过程、样本数字、选型对比引 `research/` 证据件，不复述；执行叙事（逐波落地实录）引 `log/` 收官件，不在文件头堆 dated Phase 段（`bench-trizone.md` 教训：Phase 0–2 实录已迁 `log/2026-09-22-trizone-phase0-2-进场实录.md`）。
- 引用代码写「模块 + 符号」粒度（如 `compile/engine.py::route_engine`）。行号锚点（`file.py:NNN`）只是时点快照，拆包即失效——仅用于「当时取证」语境。
- 承诺了但未实现的条目集中列在各件「未落地清单」节，不混在已落地描述里。
- 易漂移计数见 §5「计数禁入散文」。

## 5. 命名

- **日期化文件**：`YYYY-MM-DD-<topic>.md`（**前缀**式，日期为成文/冻结日期）。后续修订（迁移触碰、状态注记等）不改文件名，修订日期记入状态块；topic 语言与正文一致（中文文档用中文名）。
- **日期化目录**：`<slug>-YYYY-MM-DD/`（**后缀**式——目录按 slug 聚簇排序优先，日期殿后；范式：`dev/projects/ux-impl-2026-09-22/`、`research/product/citation-landscape-2026-09-19/`、`log/audit-2026-09-16/`）。两形不得混用：文件用前缀、目录用后缀。
- **主题页（topic page）**：无日期名仅允许给「整域统一无日期、且被代码或文档以裸名稳定引用」的域级正典件（现行范式：`research/arxiv/`、`research/corpus/`、`research/latex/` 三域全体、`spec/` 全体）。散件、新域、一次性产物一律带日期。
- **非日期主题件**：稳定小写 ASCII 连字符名。
- 文件改名/移动即引用面变更：按 §9「引用改写义务」处理。

## 6. 写作格式

- 段落写在单行内，不手工折行；`##`、`###` 分层级，不用加粗伪装标题。
- 表格只承载并列事实；长篇论证用连贯段落。
- **计数禁入散文**：规则数、文件数、测试数、篇数这类随时间漂移的计数不写进散文叙述（「adr/ 下 20 篇 ADR」增一篇即漂移成谎）。写生成口径（「见 `X` 命令」「以 `Y` 索引为准」）或在表格单元格内标注口径日期。索引表「件数」列允许计数但须与目录实况同步刷新。
- 外部来源引用用脚注：正文来源名后紧跟 `[^key]`（键为小写 ASCII 与连字符，如 `[^unarxive20]`；同一来源多处复用），行内不放裸链接；文末设 `### 参考文献` 节，逐行 `[^key]: 作者. 标题. 来源 年份. [标题或域名](链接)`。
- 行内公式 `$`，行间 `$$`；表格内公式避免裸 `|`，用 `\mid`、`\Vert` 等。
- **markdownlint 坑位**（pre-commit 会改写出来，手写时直接写对）：
    - blockquote 内空行必须带 `>`（MD028）——状态块多行引用尤常踩；
    - 表格 cell 内 `|` 必须 `\|` 转义，**在 code span 里也要**（MD056 不认栅栏语义）；
    - 表格对齐按显示宽度（CJK=2 列），重排用 `tools/md_table_align.py`；`\|` 不计宽、表头冒号吃列宽（MD060）；
    - 强调/代码 span 紧贴内容不留空格（MD037/38）；首行必须是标题（MD041）。
- **状态块适用面**：`research/`、`log/`、`dev/projects/` 包内件必备；`dev/` 顶层活文档免（README 状态列代管）。块形如：

  ```markdown
  > **结论**：一句话可带走的判断。
  > **状态**：现行 | 时点证据（YYYY-MM-DD 口径） | 已改判（→继任路径） | 已落地 | 已完成 | 已退役（YYYY-MM-DD）
  > **日期**：YYYY-MM-DD
  ```

  一次性终态（如 `已修复`、`已砍`）按实况直书即可，不必强套枚举。

## 7. 取代、退役与削除

- **单件被取代**：标题下加 SUPERSEDED 横幅，不删文件、不改写历史正文；可叠加于任意状态的件（`已落地`、`已改判` 件均有实例，非 `时点证据` 专用）：

  ```markdown
  > **⚠️ SUPERSEDED YYYY-MM-DD**：<什么判定已过期>。现状唯一事实源 = <继任者路径>；本文仅留<取证过程等>作历史参考，勿再据此派工。
  ```

  时效性结论（免费额度、默认模型、配额数字）过期等同被改判，同样处理。内部章节被单件取代时在节首加一行指针横幅（范式：`research/product/2026-09-14-competitors.md` §2 → alphaxiv-reverse）。
- **回写补注 / 落地差异注记**：实现落地与设计有出入时，在件内相关处加一条注记（差异点+日期），不改写历史正文（范式：`research/arxiv/html-path.md`）；dev 工作包则更新其 README 落地清单并以清单为权威。
- **系统退役**：活文档只留一行退役记录（拆除了什么、为什么、细节去哪查），退役详情不进散文（范式：`dev/automation.md` §1）；研究件的取证结论注明「仍有效/已失效」。
- **批量削除**：一次删除多件的，在所属域 README 立「削档清单」段——逐件列名、定性（削除/迁居）、蒸馏去向、git 历史检索法（范式：`research/README.md` §削档清单）。削除判据沿用「过程性叙事削除、结论与数字保留」。
- **不做删除**：裁决史、取证价值件一律封存进 `dev/archive/` 或留 `research/` 加横幅——本仓纪律是「不删文件，标状态」。

## 8. 敏感政策（公开发布红线）

`docs/` 随主仓公开发布。禁出现：

- 任何 key、token、密码及其形态串（含示例值）；
- 内网与 tailscale IP（`100.x.x.x`）、内部主机名；
- `~`、`/tmp/`、家目录等本机路径——产品自身路径写 `TEXLATE_DATA_DIR`、「家目录下 `.texlate/`」、「XDG state 根下 `texlate/`」这类语义形，仓内路径一律仓相对；
- 内部端口与部署细节（网关 shim、转发器、内部 systemd 实例等）；
- 个人账户信息。

LLM 网关统一表述为「内部 OpenAI 兼容网关」，不点名具体私有服务；模型名与公开 API 端点可写。开发机证据现场（`$TEXLATE_BENCH_ROOT/runs/`、`tmp/`、未入库工作区）只允许「结论已摘要进正文」式提及，不作依赖链接——fresh clone 不存在属预期。

## 9. 索引登记与引用改写义务

- 每层/每域 `README.md` 是该层索引：新件入库必须登记一行（文件 → 一句话内容）；删件同步删行。带数据/档案子目录（无 README 的裸目录不入库）首行写目录身份 + 指向父索引。
- `research/` 索引按主题域分表，新域先建域 `README.md` 再登总索引；`decisions/README.md` 是全部 ADR 的索引（含状态列）；`log/README.md` 是编年时间线。
- **引用改写义务**：移动/改名任何文档时，必须同步改写 (a) 全仓 `[x](path)` markdown 链接，(b) 代码注释中的路径串（`grep -rn 'docs/' src/ web/src/ bench/ tests/ scripts/`）——注释检索面与链接面同等硬。(c) 裸名 backtick 引用（`` `file.md` `` 不带路径）需 `grep -rn` 双查，`docs_linkcheck` 查不到它们。
- **引用优先级**：代码注释、跨层引用优先指 `spec/` 路径——`dev/` 面会流动（projects/archive 迁移是常态），spec 名不带日期天然稳定。
- 规范与 ADR 引用的裁决证据必须落在 `research/` 或仓内已入库路径；untracked 现场不作引用源（丢失与断链双重风险）。

## 10. 自动化写入位

- errsweep agent 的报告落 `research/errsweep/<date>-sweep.md`（完整契约见 `dev/errsweep-runbook.md`），域索引由报告方顺带维护。
- 其余自动化（定时任务等）不直接向 `docs/` 写件——产出落各自 results/state 区，摘要由人归档进 `log/`。

## 11. 工具链与提交纪律

- `docs/` 内 `*.md` 走主仓格式化链：markdownlint-cli2 原地改写 → md 内 python 栅栏 `ruff format` → autocorrect → prettier（git-format-staged 语义：改写暂存内容并同步工作区；改写类 hook 会 fail 一次，重新 `git add` 再提交）。细则见根 `AGENTS.md` 格式化工具链节。
- `npx markdownlint-cli2` **忽略文件参数**、按 config globs 全仓扫——验证 docs/ 时过滤其输出的 docs/ 行；表格对齐先用 `tools/md_table_align.py` 再 lint。
- 链接验证：改完跑 `python tools/docs_linkcheck.py`（跳过代码栅栏与行内 code，URL-unquote，exit 1 列死链）——只查 `[x](y)` 形，裸名引用按 §9(c) 手查。
- **`--no-verify`/私有 index 提交绕过 pre-commit** = lint 债确定源头（多会话共仓的既定提交法即此道）——绕过提交前必须手动跑一遍 markdownlint 与 linkcheck，不让债进库。
- `research/` 下数据文件（csv/jsonl/svg/tex/pdf）按各域 README 口径入库；大二进制与第三方文献原件不入库。
- 多会话共仓纪律：提交只加显式文件路径，不用 `git add -A` 全仓扫；他 lane 在飞 staged 工作不卷入本 lane commit（必要时用 `GIT_INDEX_FILE` 私有 index 提交）；不 `git stash`（别家在飞工作会被整树收走）。
