# 自带 API key（BYOK）

TeXlate 不捆绑模型服务：翻译请求发给你自己的 OpenAI 兼容端点——可以是 DeepSeek、OpenAI、Anthropic、Qwen 这类服务商，也可以是任何自建的兼容网关。三件事依次是 key 配在哪、端点要满足什么、配置之后的行为。

## 三种配法与优先级

| 配法     | 在哪配                                                                                        | 适用                                                         |
| -------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 渠道     | `#/settings` 页顶部的「渠道」卡面，或 `texlate channels`，落进数据目录的 `channels.json`      | 日常默认，存一次长期生效；多端点、凭据与回退的唯一落盘配置面 |
| 环境变量 | `TEXLATE_BASE_URL` / `TEXLATE_API_KEY` / `TEXLATE_MODEL` / `TEXLATE_DIALECT`                  | 不落地配置的启动覆盖、容器与脚本                             |
| 单次请求 | 首页高级选项的「临时 API Key」，或 `run --server` 的 `--api-key/--base-url/--model/--dialect` | 临时换个 key 或端点跑一次，不写进任何配置                    |

同一字段多处都配时的生效顺序要分两半看：key 是「请求头 > 渠道凭据 > 环境变量」；base_url、model、协议是「请求头 > 环境变量 > 渠道路由决议」——`TEXLATE_BASE_URL`/`TEXLATE_MODEL` 任一显式给出时渠道路由整体不介入，环境变量是部署者的覆盖手段，能整端盖掉界面里的渠道配置。渠道凭据自身是条阶梯：渠道内联 key > 渠道 `key_env` 指名的环境变量 > 按端点域名自动认读的专名 env（`TEXLATE_API_KEY` 兜底）。

key 的存在范围按配法收敛：单次请求的 key 只随任务生命周期留在内存，不进渠道表、任务记录、产物和日志；渠道内联存的 key 文件权限 0600，接口回读时只给「已配置/未配置」，永远不回显本体；日志对 key 形态统一脱敏。每个渠道各自记 key，切渠道不用重填。

## 端点要求

端点只要是 OpenAI 兼容即可：能接 `POST {base_url}/chat/completions`（或其他协议对应的端点）并返回标准形状。base_url 写站点根或带 `/v1` 都行，校验规则是：不允许在 URL 里嵌用户名密码或 query 参数；非本机地址必须用 https（仅本机回环与 tailnet 主机——`*.ts.net` 域名、`100.64.0.0/10` CGNAT 段地址——放行 http）。

协议（dialect）告诉客户端按哪种 API 形状说话：`auto`（缺省，按端点域名推断——Anthropic 域名自动走 messages 协议，其余按 openai）、`openai`、`anthropic`、`responses`。自建网关按它实现的 API 形状选；推断错了就在渠道的 `protocol` 字段或 `TEXLATE_DIALECT` 显式指定。

端点与模型是否真可用靠「探测」验证：渠道卡面的「探测」按钮（或 `texlate channels test <id>`）跑两段行为探针——先取模型清单验通渠道，再对所选模型发真实会话验行为；模型名拼错不会让保存失败，但会让之后每个任务在翻译阶段失败，探测是提前发现它的办法。

## 多渠道管理与路由

Settings 页顶部的「渠道」卡面（存进数据目录的 `channels.json`）是端点与凭据的唯一配置面，`settings.json` 不再存任何 BYOK 字段：卡片以 `model(redirect)` chips 展示模型清单，「编辑」开右侧抽屉分节管理——基本（名称/预设/base_url/协议/启用）、凭据、模型。「新建渠道」从服务商预设起步（预设预填 base_url/协议/推荐模型与 key env 约定名），选「自定义」留空自填。凭据二选一——内联存 key（0600 落盘、永不回显），或填 `key_env` 存一个环境变量**名**（值在环境里读，轮换 key 只改环境不改渠道）。手改 JSON 也行，格式是 `{"version":2,"channels":[…],"route":{…}}`——`models` 条目一律 `{"model":"本地名","redirect_model":"线上名","enabled":true,"max_concurrency":null}` 对象（裸字符串条目不收）；写坏的文件会被改名隔离成 `channels-invalid-*` 而不是让服务起不来，含非法条目的渠道按坏成员读径整条丢弃。

`channels.json` 缺席时首个写点（`texlate web` 启动或 `texlate channels`）会把旧配置一次性物化迁移：旧版 `endpoints.json` 档案 + 旧 `settings.json` 里的 BYOK 四键 + `connections.json` 槽位按归一化 base_url 去重合并成渠道表落盘，随后旧件改名 `*-migrated-*` 留档、settings.json 剥除那四个键；三源皆空的全新安装播种一条内建网关渠道。迁移只跑一次——之后三个旧件永不再读。

「模型」节是行式表格：每行一个本地模型名加可选的「重定向目标」——填了重定向后渠道里展示的是本地名、发给上游的是重定向名（卡片上以 `本地名(重定向名)` 显示），适合给上游长名起本地短别名。行内还有启用勾选与每模型并发上限（空=不限）。表格头排有「获取模型」（从渠道拉模型清单勾选入档）、「添加模型」、「导出模型」（复制成文本）；勾选行后出批处理条：转小写、去来源（剥 `vendor/` 前缀）、删除选中。

**路由**决定任务发到哪个渠道：卡面顶部路由条是单个选择器：留「自动」由服务端按优先级挑（`priority` 大者优先，「排序」弹窗拖拽调整即重发优先级），或钉到「渠道首选模型」/「渠道 + 指定模型」——钉选即收敛单渠道。自动模式下 `route.model` 指定想用的本地模型名时，优先选「models 显式含该名」的最高优先级渠道；全不命中回落最高优先级渠道首个可用模型。**回退**：主渠道翻译失败时按「活动渠道的其余启用模型 → 各启用备用渠道首模型」顺序换臂重试（臂名一律发重定向后的上游名），单块最多 4 条备选臂，每次切臂在任务警告里留一条 `channel_fallback` 痕；备用臂服务成功的请求会计入任务 `served_by` 审计键。失败的渠道/模型会进**冷却**（按错误分级 60s–600s：凭据失效与传输死整渠道冷却，模型故障只冷该模型，内容拒答不冷却），冷却中的组合路由时自动跳过（冷却中的渠道在设置页卡面挂徽章，钉选的渠道冷却时路由条活动行提示暂不生效）。三条硬边界：单次请求带来的临时 key 绝不发向备用渠道；你自己的 key 也绝不发向 base_url 不同的渠道——备用臂走它自己的凭据，没有凭据的远程渠道直接跳过（回环端点无 key 合法）；`TEXLATE_MODE=server` 部署形态下回退链整体关闭，渠道 API 也整面 403——多渠道拓扑由部署方管理。

**并发**是三层：Settings 的并发值是全服务在飞翻译请求总闸；渠道级 `max_concurrency` 与模型条目级 `max_concurrency` 在渠道路径上再各加一层（空=只受上层约束）。「探测」按钮（或 `texlate channels test <id>`）开测试弹窗逐模型跑两段行为探针：先取模型清单验通渠道，再对所选模型发真实会话验行为——`usable` 表示该模型保住占位符且能产出中文，`no_cjk`/`placeholder_lost` 这类判定意味着它不适合做翻译臂；子集探测只刷新被测模型的判定，其余模型的历史判定保留。命令行面还有 `texlate channels list`（渠道总览与当前路由）与 `texlate channels route [<id>|auto] [模型]`（查看/钉/清路由）。

## 模型与参数选择

「新建渠道」的服务商预设给了几个端点与推荐模型作起点（DeepSeek `deepseek-chat`、OpenAI `gpt-4o-mini`、Anthropic `claude-haiku-4-5`、Qwen `qwen-flash`），选「自定义」可填任意端点与模型名。挑模型的实用口径：翻译按段落切块逐块调用，一篇论文几百次请求，**指令遵循稳定性比峰值聪明更重要**——模型必须原样保留占位符（公式、引用、宏都被替换成了占位记号，模型只翻 prose），守不住占位符的模型会让校验器重试或回退原文。中端模型通常足够，推理型模型的长思考对段落翻译收益小、耗时大。

其余可调项：Settings 页的并发（1–16，缺省 10）是**全服务在飞翻译请求总闸**——渠道/模型各自的并发上限在它之下再细分（见上一节）；遇到限流（429）先把它调小。目标语言 zh-CN/zh-TW/en；术语表粘贴自定义对照表约束译法；「上下文提示」给每块带上标题等上下文，多数端点开着更好。

## 未配 key 的降级行为

web 任务在没有任何可用 key 时建行即落 `needs_auth` 终态——界面上补一次 key 即可续跑，不会产出占位译文。`export` 命令行则相反：没配 key 自动回落 mock 干跑并在 stderr 提示，产出的占位译文只供链路自检；要让缺 key 直接报错，设 `TEXLATE_TRANSLATOR=gateway`。

## 断点续翻与缓存

翻译是逐块记账的：每翻完一块就写缓存，任务取消、服务重启、中途崩溃都不丢已译部分，重试接着断点翻。译文缓存按「原文块 + 模型 + 提示词版本 + 语言」内容寻址——同一篇论文同一配置重跑直接命中，秒回不烧配额；换模型是另一组键，不会串译文。

单机形态下缓存默认全局共享。多用户部署（`TEXLATE_MODE=server`）默认也跨用户共享译文缓存——公开论文的翻译结果是确定性内容，共享是省钱的；但它同时是个存在性侧信道（能探出「别人是否译过某篇」），要避免可设 `TEXLATE_CACHE_SCOPE=per_key` 按 key 分桶，代价是命中率按凭证碎片化。

`needs_auth` 是唯一的缓存例外：用单次请求 key 建的任务在重启后变成 `needs_auth` 等补 key——key 不落盘是刻意的，服务端重启后拿不到它，页面上重新填一次即可续跑。

## 限额

`settings.json` 里的 `quota_max_tasks` 与 `quota_max_bytes` 给 server 形态限总量（0 为不限）；`concurrency` 是服务级在飞翻译请求总闸（渠道/模型层在其下再限，见上节）。任务级并发固定为一——队列一次只跑一篇论文，其余的排队等。
